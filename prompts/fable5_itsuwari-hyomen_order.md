# 依頼: WebGL2 リアルタイム映像作品「偽りの表面」の新規制作

## 1. 作りたいもの

Webカメラにはいつも通りの自分と風景が映る。しかしそれは偽りで、クリック/タップした
点を中心に表面が正方形ブロックとして剥離し、回転しながら物理演算で崩れ落ちて画面下に
堆積する。剥がれた穴からは本当の世界 — 彩度ゼロで味気ない、sobel 輪郭と粗い明暗だけの
白黒世界 — が露出する。剥がれたブロックは剥離した瞬間の色を凍結したまま積もり、
背後の白黒世界だけが動き続ける。放置すると表面は緩やかに自己修復し、偽りが戻ってくる。

- ファイル名: `fable5_itsuwari-hyomen.html`
- リポジトリ: `dsflon/webgl2`(単一HTML作品集。GitHub Pages で配信)

この様式の本質は「**無傷の表面は生映像そのもので、剥がれて初めてブロックだったと分かる
(騙し絵の反転)**」である。これを後処理(ぼかし・色調整・オーバーレイ)で近似しては
ならない(制作規約 失敗モード#1)。特に、**無傷面を事前にタイル分割して描くことを禁止する**
— 継ぎ目が1ピクセルでも見えたら様式は死ぬ。

## 2. 様式の参照 — 視覚的不変量表(ゲート1通過済み)

参照:
- `ref_bw_world_overflowing_aura.png` — 白黒世界の見本(公開作 overflowing_aura の背景パス)。
  彩度をほぼ落とした減色世界で sobel 輪郭が黒く抜け、面は少数トーンにポスタライズ。
  本作の裏世界はこの系統をさらに推し進め、彩度ゼロの完全白黒+輪郭線+粗い明暗のみとする
- `ref_pile_kotonoha.png` — 剛体堆積の見本(公開作 fable5_kotonoha-shigure)。個々の剛体が
  回転を伴って落下し、床と互いに衝突して自然な山なりに積もる。整列・等間隔・同位相は無い
- 騙し絵(トロンプ・ルイユ)と剥落する壁画 — 無傷のときは完全に本物にしか見えず、剥がれて
  初めて「表面が貼りものだった」と分かる。欠けは一撃では全面に及ばず、支えを失った周囲が
  時間差でパラパラと追い崩れる。破片の中の絵は剥がれた瞬間のまま止まっている

## 3. 入力映像から生き残らせる信号

- 生き残る: カメラ映像そのもの(無傷領域は無加工) / 剥離ブロック内の凍結フレーム(元位置UV) /
  裏世界での被写体の輪郭と動き(ライブ検知) / クリック・タップ・ドラッグの位置(崩壊の起点)
- 様式側で置き換わる: 剥がれた領域の実写色→彩度ゼロの白黒世界 / 映像の連続性→破片の静止した過去 /
  一様な画面→崩壊の履歴(穴・堆積・追い崩れ) / 永続する破壊→緩やかな自己修復
- 被写体(特に人物)が判読できることは受入基準である(表=実写のまま、裏=輪郭で判読)。

## 4. 技術方針(この指定に従うこと)

実装原理は次の技法語彙で固定する: 剛体物理(衝突応答+スリープ) / インスタンス描画 /
スナップショット凍結 / sobel / ポスタライズ / cell-hash / ema / ping-pong / sdf / 支持喪失伝播

パス構成の出発点(変更する場合は Phase 2 で却下理由と共に提案):

```
入力: カメラ映像 or 合成シーン(?fakesource=1 時。GLSL で動く人物+背景を合成)
[P0 scene ] cover-fit + mirror(実映像 or 合成)              sceneT  RGBA8 長辺≤1024
[P1 bw    ] sobel 輪郭 + 無彩ポスタライズ(裏世界)            bwT     RGBA8 ≤512(毎フレーム)
[P2 snap  ] 剥離イベント時のみ sceneT をスナップショット凍結   snapT[2〜3世代] RGBA8
[CPU mask ] 剥離マスク: グリッド(目安 48×30 前後)を CPU の TypedArray で管理
            クリック起点の初期剥離 → 支持喪失伝播 → 自己修復。毎フレーム小テクスチャに
            アップロード(readPixels 不要の一方向転送)
[CPU phys ] 剥離セル→剛体ボディ化(位置・速度・角速度・世代・寿命)。重力+空気抵抗+
            床/相互衝突+スリープ。堆積は列ハイトマップ近似でよい(kotonoha 方式の簡略可)
[P3 comp  ] bwT を基層に、剥離マスクで無傷領域だけ sceneT(生映像)を重ねる。
            穴の縁には紙/壁の厚みのような欠け・edge darkening を sdf 的な距離帯で少量
[P4 blocks] ボディを instanced quad で描画(snapT の元位置UV参照+風化の退色)。
            落下中の回転、堆積後の静止。ブロック側面の簡易な厚み表現は任意
```

- 外部依存: **なし**(ML モデル不使用。カメラのみ)。`?fakesource=1` は GLSL 合成シーン
  (動く人物シルエット+背景。kirie-portrait の fakeScene 方式)で全パイプラインを駆動する。
  **合成シーンには動く要素を必ず入れる**(S3 の --motion 検査が裏世界の動きを見る)。
- uDebug モード割当: 0=最終 / 1=剥離マスク(グリッド状態の可視化) / 2=裏世界のみ(bwT) /
  3=ブロックのみ(物理・スナップショット世代の確認) / 4=標本(ブロック断面見本+白黒トーン
  段階見本+崩壊伝播の縮小デモ)
- 剥離マスクは CPU 管理を推奨(グリッドは高々 48×30=1440 セル。GPU ping-pong にする場合は
  その理由を Phase 2 で述べること)。物理は CPU で毎フレーム O(ボディ数)。
  スリープと寿命消滅でボディ数を有界に保つ。
- スナップショット凍結は copyTexSubImage2D(sceneT を FBO にバインドして読む)等の
  GPU 内コピーで行い、CPU 経由の readPixels を使わない。

## 7. 制約条件(dsflon/webgl2 リポジトリ規約 — 受入基準を兼ねる)

### 成果物の形
- 単一の自己完結 HTML。外部ライブラリ・ビルド工程・外部アセット禁止
  (例外: ML モデルのみ CDN 可。本作の許可: **なし**)。
- WebGL2 / GLSL ES 3.00。WebGL1 フォールバック不要。
- ファイル冒頭に HTML コメントで: 作品概要 / 実行方法 / 様式解析の要約 /
  パイプライン図 / 全スライダーの説明 を書くこと。
- README.md の作品リストに GitHub Pages の URL を追記すること(S5 でオーケストレータが行う)。

### カメラ
- getUserMedia は facingMode 指定(user/environment)。モバイルでは切替ボタンを表示。
- <video> は playsinline muted autoplay。ミラーはシェーダの UV 反転で行う。
- 非セキュアコンテキスト / 権限拒否 / カメラ無し の3経路それぞれに、
  専用メッセージと再試行ボタンを持つオーバーレイを表示すること。
- カメラとキャンバスのアスペクト比差は cover-fit(切り取り)で吸収すること。

### UI(既存作品の panel 構造を踏襲)
- 実装前に `fable5_papercraft-cam.html` を読み、カメラ取得・UIパネル・エラー表示・
  PNG保存の規約を踏襲すること(**参考にするのは規約定型のみ。作品表現は参考にしない**)。
- 全パラメタは単一の state オブジェクトに集約し、スライダー定義は
  [key, ラベル, ヒント, min, max, step] の配列から生成すること。
- DEFAULTS と「RESET LOOK」。「HIDE UI」「SAVE PNG」(preserveDrawingBuffer: true)。
- prefers-reduced-motion 時はアニメーション停止トグルを初期 ON。

### 検証フック(機械検証が依存する。必須)
- window.__artReady: 最初の本描画フレーム完了時に true を立てること。
- ?freeze=1: 時間駆動アニメーションを停止し決定的な静止フレームを出すこと
  (合成シーンも静止。物理も停止)。
- ?prewarm=<秒>: 初回描画の前に、指定秒ぶんのシミュレーションを固定 dt で
  決定的に早送りしてから開始すること(freeze の preroll と同じ機構を非 freeze にも
  公開する。検証環境はソフトウェアレンダリングで実時間 warm が数分かかるため、
  「絵が育った状態」のスクショをこのフックで数秒で撮る)。**prewarm 中に決定的な
  スクリプトイベント列(クリック相当の剥離イベント2〜3発)を発生させ、穴・落下中の
  ブロック・堆積・追い崩れが揃った状態を作ること**(スクショと Checker の一次証拠になる)。
- ?fakesource=1: カメラ/権限を一切使わず、GLSL 合成シーン(動く人物+背景)で
  全パイプラインを駆動できること。
- ?fakescale=: 人物マスク駆動ではないため**該当なし**(実装不要)。

### 品質基準
- 静止したカメラの前で画面がチラつかないこと(乱数シードはセル座標由来)。
- デスクトップ 60fps / モバイル 30fps 以上(DPR 上限 2、重いバッファは解像度上限)。
- リサイズ・カメラ切替・タブ復帰で壊れないこと(リサイズ時はグリッドとボディを
  安全に再構築してよいが、クラッシュ・NaN 化しないこと)。

## 8. 技術注意リスト(遵守すること)

1. GLSL ES 3.0 の予約語を変数名に使わない: coherent, sample, filter, precise,
   restrict, readonly, writeonly, subroutine, input, output, common, partition, active
2. 同一テクスチャを read しながら write しない。feedback/拡散/EMA は必ず ping-pong。
3. float テクスチャは EXT_color_buffer_float を確認し、未対応時の代替を用意
   (本作は RGBA8 のみで成立させられる構成を推奨)。
4. MRT のブレンドは全アタッチメント共通。クリアは clearBufferfv を毎アタッチメント。
5. 方向場は二重角 (cos2θ, sin2θ)。角度の直接 lerp をしない。
6. normalize(ゼロベクトル) は NaN。pow(x,y) は x<0 で未定義。
7. ループは const int MAX + break。
8. 頂点シェーダのテクスチャ参照は textureLod。
9. 乱数は pcg系 hash12。シードに時間を混ぜない(cell-hash はセル座標のみから)。
10. UNPACK_FLIP_Y_WEBGL は DOM ソースのみ。TypedArray アップロードはシェーダ側で向きを合わせる。
11. gl_PointSize は使用しない(ブロックはインスタンスクアッド)。canvas は
    preserveDrawingBuffer: true。
12. UV・位置計算は highp。
13. ブラーは縦横分離。readPixels を毎フレーム呼ばない(剥離マスクは CPU→GPU の一方向)。
14. 剥離ブロックの継ぎ目禁止は「無傷面」の話である。剥離した穴の縁と破片の輪郭は
    むしろはっきり見せてよい(欠けの実在感)。
15. スナップショット世代テクスチャは剥離イベント時のみ更新(毎フレーム copyTex しない)。
16. 物理ボディはスリープ(静止判定で計算除外)と寿命消滅を必ず実装し、
    ワーストケース(全セル剥離)でも 60fps を維持できるボディ数上限を設ける。
17. ドラッグ/タッチムーブでなぞった軌跡に沿って連続的に剥離できること
    (pointerdown 単発と pointermove の両方)。

## 9. 検証環境

- フェイクカメラ+スクリーンショットは `loop/runner/`(testscene.mjs / verify_runtime.mjs)
  を使う。ローカルサーバは python3 -m http.server 8888。
- スクリーンショットは (a) 最終合成 — **`?fakesource=1&prewarm=12` で穴+落下+堆積が
  揃った状態**(実時間 warm 禁止: swiftshader では数分かかる) (b) uDebug の主要モード
  (c) ?fakesource=1 の標本 の3枚以上。pageerror が出ていないことを毎回確認する。
- 蓄積系(堆積・修復で絵が育つ)のため `verify_runtime --longrun` で
  長時間安定(whiteout/発散なし・ボディ数有界)も確認すること。
- 時間軸の不変量(#2 #5 #6)があるため `--motion` も必ず通ること(裏世界のライブ性と
  落下ブロックの運動が対象。合成シーンの動く要素で担保)。
- **実機乖離の予防**(`loop/CRAFT.md` §C を実装前に読むこと):
  外部検知なしのため fakeseg は「該当なし」と報告してよい。ただしモバイル性能レシピ
  (CRAFT §C3: DPR 上限・バッファ解像度上限・pointer 種別の扱い)は踏襲すること。
- 検証できない項目(実機カメラ・実機GPU 依存)は「未検証」と明記し、
  確認すべき点を列挙すること。

## 10. 自己批評ルーブリック(スクリーンショット取得後、報告の前に実行)

1. §2 の不変量表の各行を画像と照合し 5 段階で自己採点(存在しなければ1点+理由)。
2. 「縮小して見た印象」(様式の成立)と「等倍で見た印象」(構造の正しさ・誤魔化しの有無)を分ける。
3. 最低点の2項目に、制作規約 §10 翻訳表の語彙で修正案を出す。
4. 自己批評の自走は**1周まで**(明確な破綻の修正のみ。美的な磨き込みは S4 の独立
   レビューの領分 — 自走の重複はループ全体を遅くする)。採点は甘くしない。

## 11. 報告様式

各フェーズの最後に: 「成果物 / 自分で確認したこと / 未確認のこと / 判断に迷った点」の4項目。
受入基準にない機能は実装せず提案に留めること。
