# アート制作ループ — 構想と方針(Art Loop Design)

テーマを1つ与えると、発注プロンプトの作成 → 実装 → 検証 → 美的レビュー → 修正を
**人間の逐次指示なしに再帰的に回し**、極めて質の高い WebGL2 リアルタイム映像作品を
main への PR として提出するシステムの設計書。

- 方法論: [loop/LOOP_ENGINEERING_GUIDE.md](./LOOP_ENGINEERING_GUIDE.md)(以下「指南書」)
- 品質の下位層(プロンプト・ハーネス): [AI_DIRECTION_GUIDE.md](../AI_DIRECTION_GUIDE.md)(以下「制作規約」)
- 実装手順: [loop/IMPLEMENTATION_PLAN.md](./IMPLEMENTATION_PLAN.md)

> 指南書 §1.1 の言葉で言えば、このリポジトリには既に
> **Prompt 層**(制作規約 §3 テンプレート・§5 語彙辞典)と
> **Harness 層**(制作規約 §4 規約ブロック・§7 検証環境・§9 技術注意)が存在する。
> 本設計はその上に **Loop 層** — 人間抜きで回り、正しく止まるシステム — を載せる。

---

## 1. 位置づけと現在資産

これまでの制作(fable5_van-gogh, fable5_papercraft-cam 等)は
「人間が制作規約を使って毎回ディレクションする」運用だった。実績として:

- 制作規約のフェーズ制(様式解析→設計→標本→実装→検証)が品質を出すことは実証済み
- 発注書の実物が**1種**存在する(`prompts/fable5_papercraft-cam_order.md`。
  サンプルが1つしかない事実は Phase 2 のリスクとして扱う → 実装計画)
- フェイクカメラ+Playwright スクリーンショットによる自己検証も実運用済み

**足りないのはループの5動作**(指南書 §2)のうち、人間が担っていた部分の外部化:
ゲート審査の機械化・状態の永続化・サーキットブレーカー・人間 Inbox の明文化である。

## 2. ループ化の適格性と自律度(指南書 Step 0)

3条件の確認:

| 条件 | 判定 | 根拠 |
| --- | --- | --- |
| 繰り返し発生する | ✅ | テーマは無数(様式 × 入力信号 × 技法の組合せ)。テーマキューで供給 |
| 検証可能 | ⚠️ 部分的 | 動作品質・規約準拠は機械検証可能。**美的品質はそのままでは不可** → §4 で3層に翻訳する |
| 境界が明確 | ✅ | 1作品 = 単一の自己完結 HTML + 発注書。外部副作用は PR 提出のみ |

**自律度は L2 Assisted で開始する。**

- 自動: 発注書生成・実装・決定的検証・美的レビュー・修正・ブランチへの push・PR 作成
- 人間ゲート: **main へのマージ**(= 外部反映)。PR が dry-run 提示に相当する
- L3(cron 起動・自動マージ)は運用指標が安定してから検討(§9)

## 3. 正解の実物(指南書 Step 1)

新しく仕様を発明しない。「合格した作品はどういう形をしているか」は実物から採る:

- **成果物の実物**: `fable5_van-gogh.html` / `fable5_papercraft-cam.html`
  (規約ID・ヘッダコメント構成・エラー3経路・UIパネル構造・検証フックの採取元)
- **発注書の実物**: `prompts/fable5_papercraft-cam_order.md`(発注書 lint の採取元)
- **ディレクション記録の実物**: 制作規約 §11 のケーススタディ
  (美的レビューの語彙・修正粒度±15〜35% の採取元)

> **フィクスチャの線引き**: 規格フィクスチャ(V1 lint に全項目合格することを期待する実物)は
> **`fable5_papercraft-cam.html` のみ**。`fable5_van-gogh.html` はヘッダ5節構成や
> 検証フック(`__artReady` 相当)を持たない旧規格であり、規約ID・語彙・様式解析の
> **採取元としてのみ**使う(lint 適合は期待しないし、追補もしない)。
> 「合格の実物が検証器に落ちる」という Validator-First の矛盾を避けるための明示的な区別である。

## 4. 「合格」の翻訳 — 3層の検証(指南書 Step 2, §3)

美的品質を丸ごとループに渡すと「品質を改善する」型の検証不能ゴールになり、
スロップファクトリー化する(指南書 §3.1)。そこで合格を3層に分解し、
**機械検証できる層を厚くし、できない層は人間の領分として明文化する**:

### V1 決定的検証(コード。LLM 不使用。ループの停止条件)

制作規約 §6「コードを全部読まずに検査する」を機械化したもの。

- **静的 lint**(`loop/runner/verify_static.mjs`):
  - 必須構造: ヘッダコメント5節(概要/実行方法/様式解析/パイプライン図/スライダー)、
    規約ID(`#togglePanel` `#savePng` `#resetLook` `#overlay` `#readout` ほか)、
    `playsinline` / `preserveDrawingBuffer: true` / DPR 上限 / `facingMode`
  - 禁止パターン: GLSL 予約語の変数使用、マーク配置シードへの `uTime` 混入、
    外部ライブラリ参照(ML 例外の許可リスト以外)
  - 要求パターン: EMA/feedback 系での ping-pong、エラー3経路の文言、
    検証フック `window.__artReady`(§5 で規約化)
- **実行時検証**(`loop/runner/verify_runtime.mjs`。Playwright + フェイクカメラ):
  - `pageerror` 0件(シェーダコンパイル失敗の検出器)
  - `__artReady` 到達 / 黒画面でない(キャンバス輝度サンプリング)
  - **フリッカ検査**: `?freeze=1`(時間駆動停止スイッチ、§5 で規約化)+静止テストシーンで
    数秒おきの2ショットの画素差分が閾値以下(「チラつかないこと」の決定的翻訳。
    freeze なしの差分では「意図したアニメーション」と「不要なフリッカ」を分離できない)
  - 全スライダー両端掃引・全デバッグビュー・リサイズ×2・UIトグルで生存
  - カメラ拒否経路で専用オーバーレイが出る
- エラーは指南書 §3.2-3 の形式(機械可読・フィールド単位・修正ヒント付き)で返す。
- **静的 lint の線引き**: 停止条件(severity=error)にするのは**決定的に判定できる
  近似ルールだけ**。意味理解を要する検査(ping-pong の正しさ、シード純度の厳密判定)は
  テキストパターンでは誤検出/見逃しが必至のため、限定パターンの warning
  (V2 への申し送り事項)に落とすか V2 のチェック項目へ回す。線引きの明文化は
  実装計画 Phase 1 の受入条件。

### V2 構造化 LLM 検証(Maker-Checker 分離。美的品質の一次レビュー)

コードで書けない「様式が成立しているか」は、指南書 §3.2-2 に従い
**生成役と別の役割(Checker サブエージェント)**が、**「拒否する理由を探す」姿勢**で行う:

- 入力: スクリーンショット一式(最終・縮小・等倍クロップ・デバッグビュー)+
  その作品の**不変量表**(発注書に含まれる。作品固有のルーブリック)
- 出力: `review.schema.json` に適合する JSON —
  不変量ごとの 1〜5 採点・不合格理由・制作規約 §10 の語彙による修正指示
- 合格条件: 全不変量 ≥4 を **2回連続**。定義: **同一成果物(同一コミット)に対して、
  文脈を共有しない独立の Checker 実行を2回**行い、いずれも全不変量 ≥4 を返すこと。
  再採点であって再生成ではないので「合格後の再生成禁止」(指南書 §5.1-1)と矛盾しない。
  1回目合格・2回目不合格なら2回目のエラーリストで修正ループへ戻る(成果物が変わるため
  カウントはリセット)。狙いは、採点の非決定性による**偽合格(1回の甘い採点)を
  直列 AND で抑える**こと。副作用の偽不合格(良品が運悪く落ちる)は修正ループと
  attempts 上限が吸収し、needs_review 側に倒れる — 甘い方向には倒れない
- 出力自体はスキーマでコード検証する(壊れたレビューはリトライ)
- Checker のプロンプトはテンプレート固定(`loop/templates/checker_prompt.md`)。
  Maker の実装文脈を見せず、スクショと不変量表だけを渡す(自己評価バイアスの遮断)

### V3 人間レビュー(検証器に入れない品質。明文化された領分)

制作規約「外部化できないもの」と同じ3つ+1つ。**PR 上で行う**:

1. 趣味判断 — どこで「完成」とするか
2. 不変量表(様式解析)の真偽照合 — もっともらしい捏造の検出
3. 未知の失敗への対応
4. マージ判断そのもの(L2 ゲート)

PR には人間が数分で判断できる材料を必ず添付する: スクショ一式・不変量表・
V1/V2 の結果サマリ・needs_review 事項(§8 Inbox)。

## 5. リポジトリ規約への追補(ループ対応)

ループが機械検証できるよう、制作規約 §4 に次を追加する(3点同期の起点):

- **`window.__artReady`**: 最初の本描画フレーム完了時に true を立てる(全作品必須)
- **`?fakesource=1`**(推奨): 外部依存(MLモデル等)なしで様式パイプラインだけを
  駆動できる合成入力スイッチ(papercraft-cam の `?fakedepth=1` の一般化)
- **`?freeze=1`**(必須): uTime 等の時間駆動アニメーションを停止し、決定的な静止フレームを
  出すスイッチ(既存作品の「Pause」トグルの URL 化)。V1 のフリッカ検査・スクショ再現は
  この状態で行う
- 発注書は必ず**不変量表を機械抽出可能な表形式**で含む(V2 のルーブリック源)

## 6. パイプラインのステージ分解(指南書 Step 3)

各ステージに 入力/出力/完了条件/失敗時遷移 の4点を定義する:

| # | ステージ | 入力 | 出力 | 完了条件(検証) | 失敗時 |
| --- | --- | --- | --- | --- | --- |
| S0 | brief(様式解析) | テーマ1行 | `loop/state/<slug>/brief.json`(不変量表・参照作品・生き残らせる信号・技法語彙) | `invariants.schema.json` 適合(5±2個。列構成は発注書の実物に準拠: 不変量/担当軸/実装原理/外した場合+優先順。出典は行単位または brief の参照リストで必須) | 再試行→needs_review |
| S1 | order(発注書生成) | brief | `prompts/<slug>_order.md` | 発注書 lint(必須節・規約ブロック・技術注意・スライダー6〜10・§5語彙≥3) | 再試行→needs_review |
| S2 | implement(実装) | 発注書 | `fable5_<slug>.html` | V1 静的 lint 全合格 | 修正ループ→needs_review |
| S3 | runtime(動作検証) | S2 の HTML | スクショ一式+検証レポート | V1 実行時検証 全合格 | 修正ループ→needs_review |
| S4 | aesthetic(美的レビュー) | スクショ一式+不変量表 | `review.json`+修正差分 | V2 全不変量≥4 ×2連続 | 修正ループ→needs_review |
| S5 | submit(提出) | 全成果物 | ブランチ push+PR(Inbox サマリ付き) | PR 作成 API 成功 | needs_review |

- S2〜S4 の修正は指南書 §5.1 の規律に従う:
  エラー原文をそのまま Maker に戻す / 指摘箇所以外を変えない / 合格後の再生成をしない。
- 修正内側ループは指南書 Step 6 の擬似コードをそのまま移植する。

## 7. 状態・Discovery・Trigger(指南書 Step 4)

- **状態の外部化**: `loop/state/<slug>/state.json`
  — `status` / ステージ別 `attempts` / `last_error`(原文) / `requires_human` /
  `updated_at` / `cost`(トークン・周回数)。遷移の追記ログは `loop/state/<slug>/log.jsonl`。
- **状態名はステージ完了形**: `briefed → ordered → implemented → runtime_ok →
  aesthetic_ok → submitted` + `needs_review` + `failed`。全状態に出口がある
  (needs_review は人間の指示で該当ステージへ戻す)。
  **強制終了→再実行で、状態ファイルだけを頼りに続きから回る**ことを受入条件とする。
- **Discovery**: `loop/themes.md` のテーマキュー(人間が1行1テーマで追記)を走査し、
  state が無い/未完了のテーマを優先度順に選ぶ。
- **Trigger**: 当面は人間の一度きりの指示(スキル `/art-loop <テーマ>` または
  `/art-loop next`)。cron 化は指標安定後(§9)。

## 8. Maker-Checker の配役と人間 Inbox(指南書 §3.2, §6)

```
オーケストレータ(メインエージェント)
  ├─ S0/S1 Maker: 発注書ライター(制作規約 §3 テンプレを埋める)
  ├─ S2 Maker: 実装者サブエージェント(入力は発注書のみ。会話文脈を持たない)
  ├─ V1 Checker: コード(loop/runner/*.mjs) — LLM 不使用
  ├─ V2 Checker: 美的レビュアーサブエージェント(拒否志向・実装文脈なし・
  │              可能なら別モデル設定)
  └─ Inbox: loop/state/ の needs_review 一覧 + PR コメント
```

- **Inbox の要件**(指南書 §6): needs_review には「エラー原文・スクショ・修正案・
  収束しなかった理由の仮説」をセットで残し、人間は選ぶだけにする。
- **人間の判断は還元する**: PR レビューでの指摘は、その場限りにせず
  「V1 の新 lint ルール」「V2 ルーブリックの新軸」「制作規約 §1 の新しい失敗モード行」
  のいずれかに翻訳して追加する(§9 メタループ)。

## 9. サーキットブレーカーと運用指標(指南書 §3.3, §7)

- **試行上限**: S0/S1 各2回、S2 静的修正3回、S3 実行時修正3回、S4 美的修正3周。
  超過は失敗ではなく needs_review への正常な出口。
- **タイムアウト**: 1テーマ1実行あたりの壁時計上限(初期値 60分)。
- **コスト記録**: 周回ごとに `state.json` の `cost` へ記録し、実行サマリに出す。
- **計測する指標**: 収束率(人手ゼロで submitted に到達した率)/ needs_review 率 /
  ステージ別平均 attempts / コスト。
- **メタループの規約**: 合格の定義(スキーマ・lint)・生成(発注書テンプレ・Maker指示)・
  検証(runner・checker プロンプト)は**必ず3点セットで同期変更**する。
- **L3 への昇格条件**(将来): 直近 N テーマで収束率・コストが安定し、
  自動マージしてよい変更の許可リスト(新規ファイル追加のみ・既存作品は不可変更、等)を
  明文化してから。

## 10. リスクへの態度(指南書 §8)

| リスク | 本システムでの対策 |
| --- | --- |
| Verification の甘さ | V1 を厚くし続ける(人間指摘の lint 化)。V2 は「2連続合格」+拒否志向で甘さを抑える |
| 理解の負債 | PR に不変量表・スクショ・検証サマリを人間可読で必ず添付。1テーマ=1PR で差分を小さく保つ |
| 認知の降伏 | マージ判断(V3)を自動化しない。L3 昇格は §9 の条件を満たすまで禁止 |
