# TECHNIQUES.md — 表現手法カタログ(スカウトの判断材料)

> **これは何か**: テーマ(What)に対して**最適な表現手法(How)を選ぶ**ための
> レパートリー表。`/art-scout` がテーマ×手法のマッチングに使い、S0 brief の
> 手法決定の根拠になる。CRAFT.md が「失敗の知識」なら、本書は「選択の知識」。
>
> **更新規律**: 新作が submitted になるたび、その作品の 入力×エンジン と
> 得られた教訓(得意/不得意の追記)を本書に反映する(メタループの一部)。
> 実績のない手法を実績ありに見せかけない。

---

## 0. 選択の原則

1. **テーマの本質が先、手法は後**。「このテーマの本質は何か」を一言で言語化して
   から表を引く(身体の変容か / 環境の光か / 群れの運動か / 音のエネルギーか /
   物質の質感か)。
2. **Webカメラ・MediaPipe は前提ではない**。人が主役でないテーマに人物検知を
   持ち込まない。無入力の純ジェネラティブも対等な選択肢。
3. **多様性ガード**: works.json の日付降順で直近 2 作が使った「入力」と
   「主エンジン」には減点を付ける(同じ組み合わせの連投を避ける)。
4. **検証強度は採点に入れる**(§3)。同点なら検証強度が高い= sandbox で
   完全検証できる手法を優先する。
5. **実績のない手法は「挑戦枠」として明示**して選んでよいが、その場合は
   リスク(検証不能領域・CRAFT 該当項目なし=地雷未知)を brief に書く。

## 1. 入力レイヤ(何に反応するか)

| 入力 | 得意なテーマの本質 | 実績(作品) | リスク・注意 | 検証強度 |
|---|---|---|---|---|
| **MediaPipe 人物検知**(セグメンテーション±Pose) | 身体の変容・「人が○○になる」・図地(人型)が主役 | mosaic / flower-being / gas-head / oneline / scribble / typo / water-cam / overflowing_aura 系 / live_portrait | CRAFT §C 全部(Y反転・スケール・モバイルrecipe必須)。Pose は必要時のみ(C3) | **V-C**(要実機注記が残る) |
| **Webカメラ映像のみ**(検知なし) | 環境・光・色彩の変換。人が写ってもよいが主役は画面全体 | van-gogh / ascii / smoke-portrait / blue-dissolve | 検知がないぶん軽量・実機乖離が小さい | **V-B**(fakesource で概ね完結) |
| **マイク音声** | 声・音楽・爆発的イベント・エネルギーの可視化。音の言語化(文字・オノマトペ) | ds_voice / overflowing_aura_4taigyo 系(音声コマンド) / dogra-magra / kotonoha-shigure(音→墨の活字) | 無音時の見た目を必ず設計(音がなくても成立する絵)。実マイク・Web Speech(ネット必須)は sandbox 検証不能=目視の領分 | V-B(合成イベント列で主要経路を検証可) |
| **ポインタ/タッチ** | 触れる・かき混ぜる・介入する遊び | suibokuga_sakana(水面かき混ぜ) / ds(粒が逃げる) | 触らない時間が大半 — 放置状態が主役級に美しいこと | **V-A**(完全オフライン検証可) |
| **無入力**(時間のみ・純ジェネラティブ) | 自然現象・群れ・抽象・成長するシステム | iwashi_ball(Boids) | 実機乖離ゼロ。単調化に注意(決定論+ゆらぎの設計) | **V-A**(sandbox で 100% 検証可) |

複数入力の併用は可(例: 検知+音声 = overflowing_aura 系)。ただし主入力を 1 つ
決め、副入力は「なくても成立」する設計にする。

## 3. 検証強度(スカウト採点用)

| 等級 | 意味 | PR に残る注記 |
|---|---|---|
| **V-A** | sandbox で完全検証可(無入力・ポインタ) | なし(全チェック済みと言い切れる) |
| **V-B** | fakesource / 合成音源で主要経路を検証可(映像のみ・音声) | 実カメラ/実マイクでの見え方のみ軽微な未検証 |
| **V-C** | MediaPipe 実推論が sandbox 不能(検知もの) | 「実機で要確認」が必ず残る + CRAFT §C 対策一式が必須コスト |

## 4. マッチング手順(スカウトが従う)

```
テーマ候補
  → 本質を一言で言語化
  → 入力レイヤ表・エンジン表から候補 1〜2 組を引く
  → 採点: 本質適合(0-5) + 検証強度(V-A:+2 / V-B:+1 / V-C:+0)
          − 多様性ペナルティ(直近2作と入力かエンジンが同じ: 各−2)
  → 最高点の 入力×エンジン を採用。次点と却下理由を必ず記録
```

- 採点は目安であり、**本質適合が 5 なら他の減点を覆してよい**(テーマに MediaPipe
  が本質的に必要なら V-C でも選ぶ)。その場合は覆した理由を明記する。
- 決定は brief(S0)に「手法決定」として書き、Maker は勝手に変更できない。
